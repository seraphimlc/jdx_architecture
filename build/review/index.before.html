BilionPass 平台说明

把本地服务供给，接进既有大渠道
业务 · 系统 · 规划 ｜ v0.2（业务全景图 + 2 篇样例） ｜ 更新 2026-09-29　事实来源：CTO 口述 + v1 架构图转录。文中【事实】为 CTO 确认，【判断】为整理者推断，【待确认】为尚未澄清。

业务全景

对渠道而言，BilionPass 是服务供给商——我们整合一系列日本本地服务交给渠道，用来丰富渠道自己的能力。
对旅客而言，BilionPass 是自有平台（bilionpass.com / APP / 小程序）。

每个框都能点开，看它自己的说明。

状态：在跑对接中 / 待推广 开发中规划中 / 未上线

平台能力现状

平台系统件都已自研在跑，但能力层很薄——11 项里只有 4 项在跑，其中结算、风控、履约三项都还没做。

关键诊断 已确认

按 CTO 确认的优先级排序：结算 > 风控 > 履约。

优先级 1
结算
现状：手工对账
全业务过账 + 多分账对象（机场、佐川、JTR、Jalan、Canlead）+ 多规则（门票酒店 5% 佣金、退税 15% 手续费）+ 跨中日资金，全靠手工。业务量一涨即卡死，差错直接是钱。
优先级 2
风控
现状：无
代收全款 + 手工对账 + 零风控三重叠加：支付风险、退款欺诈、渠道套利、对账差错都没有系统兜底。
优先级 3
履约
现状：仅空手行与佐川打通
单点已通；通用履约能力（服务履约 / 其它履约）不存在 → 每新增一个需履约的业务（租车、预约核销、门票核销）都要重接一次。

BilionPass 在跑

端

面向赴日中国旅客与全球游客的自有平台（C 端）。

服务对象：C 端旅客 · 中国客群与全球游客 · 来源：CTO 口述

现状

  • 自有端构成：bilionpass.com（日本站）· APP · 微信小程序 · WEB。
  • 在自有端卖的东西：行前购（自营在线商城，在跑）、空手行（在跑）、留学缴费（跳转 fintech）。
  • 它覆盖的是另一批客群：渠道（携程、东航）都是中国的，只覆盖中国客群；自有端承担非中国客群 / 全球游客（空手行这类服务本身无国籍门槛）。
  • 台湾站：规划中，年底上线（官网不一定有）。

依赖 / 协作

供给方机场（羽田 / 成田 / 关西） · 佐川物流 · fintech
中枢职能
分发线自有端（自己卖）

下一步规划

  • 台湾站年底上线（与日本站是独立建站，不是同一套系统多站点——业务形态不同）。
  • 【待补】自有端要不要承担更多内容（目前渠道只接了空手行、优惠券）。

【判断】

  • 自有端与渠道端按客群互补，不是主次关系——所以"我们不做自有推广"应理解为"不自建流量，但自有端要接住渠道覆盖不到的那部分客群"。

【待确认】

  • 自有端与渠道侧的销量占比
  • 台湾站到底有没有面向 C 端的官网

外部渠道 在跑

分发出口

内容池的主要分发去向——我们以"服务供给商"的身份把内容接进渠道，丰富渠道自己的能力。

服务对象：渠道的中国客群（携程用户、东航会员） · 来源：CTO 口述

现状

  • 目前只接了 3 条：携程 → 空手行（API 对接）；东航 → 空手行（嵌入 H5 页面）；东航 → 优惠券（人工上传，券信息/券码由我们人工传到东航后台，没有系统对接）。
  • 三种形态：上架销售 · 会员权益 · 积分消耗（暂不涉及联合营销）。例：酒店给到东航可作为会员权益 / 积分消耗。
  • 资金模式由接入形态决定（通则）：API 对接 → 渠道收款后按周期结算给我们；H5 嵌入 → 我们页面成交、钱直接到我们账。

依赖 / 协作

供给方
中枢职能③ 资金与结算 · ④ 分发与授权
分发线外部渠道

下一步规划

  • 渠道扩（把门票/酒店等接给更多渠道）：等商务侧计划，不列入技术规划。
  • 【待补】现有 3 条里，优惠券那条要不要从人工上传改成系统对接。

【判断】

  • 授权的真实维度是「渠道 × 内容 × 形态」，不是"渠道 × 业务"——同一份内容、不同渠道、不同形态（空手行在携程是上架销售，酒店在东航可能是权益/积分）。
  • 内容池有 9 块内容，真正上渠道的只有 2 块（空手行、优惠券），差距很大。

【待确认】

  • 哪些渠道能拿哪些内容、以什么形态给
  • 渠道佣金怎么结（是否抽成、周期）

行前购 在跑

产品与服务内容

机场免税店线上下单、离境时在机场取货。

服务对象：赴日中国旅客 · 来源：CTO 口述

现状

  • 性质 = 代运营：系统是我方自研（C 端 + B 端），货是免税店的，钱过我们账，运营方也是我们公司（B 端后台给机场运营方用，管商品与订单）。
  • 商品与库存：通过 API 从免税店系统同步——权威源在免税店那边，我们做的是同步、映射、上架、下单。
  • 机场：羽田 / 成田 / 关西；机场是我们的股东 / 投资人。
  • 货架位置：目前只在自有端（我们自营的在线商城）；渠道侧尚未推商品销售。

依赖 / 协作

供给方机场（羽田 / 成田 / 关西）
中枢职能① 商品与库存 · ③ 资金与结算
分发线自有端（自己卖）

子图表

下一步规划

  • 12/30 前：关西机场行前购上线。
  • 【待补】羽田 / 成田 现在是否已在跑（关西是第三个，还是其中一个还没上）。

【判断】

  • 行前购和空手行虽然同属"我们闭环"，但外包出去的东西不一样：行前购外包的是货，空手行外包的是运力——架构上关心的东西不同（前者关心货的信息与结算，后者关心履约过程与状态）。

【待确认】

空手行 在跑

产品与服务内容

旅客到机场后把行李交给我们，我们定时送到酒店——让旅客空手出行。

服务对象：既有 C 端旅客（经渠道与自有端） · 来源：CTO 口述

现状

  • 供给：与佐川物流合作履约（佐川是我们的股东）；业务系统由我们自研。
  • 分发：携程（API 对接）、东航（嵌入 H5 页面）、自有端（也在卖）。
  • 资金：钱走我们账。携程模式 = 渠道收款后结算给我们；东航 H5 = 我们页面成交、钱直接到我们账。之后再与佐川分账。
  • 履约：已与佐川系统 API 打通，线上在跑——这是目前唯一跑通的履约链路。
  • 自有端的意义：渠道（携程/东航）只覆盖中国客群；空手行这类服务本身无国籍门槛，自有端可面向全球游客。

依赖 / 协作

供给方机场（含免税店） · 佐川物流
中枢职能② 订单与履约编排 · ③ 资金与结算 · ④ 分发与授权
分发线外部渠道 · 自有端

子图表

下一步规划

  • 【待补】服务范围与时效的目标（目前只知道"机场 → 酒店、指定时间内送达"）。
  • 【待补】是否要把这条链路作为其他业务接渠道的复用样板。

【判断】

  • 空手行是目前唯一同时跑通"渠道对接 + 履约编排"的业务，因此它是这两件事的现成样板——其他业务接渠道、接履约时，最省力的做法是先看空手行是怎么接的。
  • 它是"两条分发线互补"的最好例子：渠道拿中国客群，自有端拿全球游客。

【待确认】

  • 服务范围与时效（只能机场→酒店？几小时内送达？）
  • 计费方式（按件 / 按重 / 按距离）
  • 自有端与渠道侧的销量占比

③ 资金与结算 部分（资金在跑 / 结算手工）

中枢（不在全景图上，从左侧导航进）

所有业务的收款、分账、对账——平台的主动脉。

服务对象：全部业务的旅客资金与供给方分账 · 来源：CTO 口述 + 已确认的资金模式通则

现状

  • 所有业务的钱都走我们账（唯一例外：留学缴费，钱不过账）。
  • 资金模式由集成形态决定（已确认的通则）：API 对接 → 渠道收款后按周期结算给我们；H5 嵌入 → 我们页面成交、钱直接到我们账。
  • 对手方是双向的：对渠道可能收也可能付（有的渠道结算给我们，有的我们付佣金给渠道）；对供给方是付（分账 / 佣金 / 手续费）。
  • 规则随"渠道 × 业务"变：门票酒店按营业额 5% 抽佣（初步）；退税收退税额的 15% 手续费（例：消费 10000 → 退税 1000 → 退游客 850、我们留 150）。
  • 结算现状：手工对账。 风控现状：无。
  • 佣金结算目前不是系统自动分账。

依赖 / 协作

供给方机场（含免税店） · 佐川物流 · JTR · Jalan · Canlead
中枢职能④ 分发与授权（决定谁能卖、怎么结） · ⑧ 账号与权限（KOL 分佣要归因） · ⑨ 主数据
分发线外部渠道 · 自有端 · 社媒与 KOL（KOL 分佣）

下一步规划

  • 这是 CTO 确认的第一优先级（排序：结算 > 风控 > 履约）。
  • 【待补】系统化的范围：先做哪些对手方、哪些业务。
  • 【待补】合规与牌照问题（全业务代收 + 多方双向分账）。

【判断】

  • 结算的复杂度 = 对手方 × 方向 × 规则 × 地域货币，手工在这四个维度上不可持续。
  • 渠道授权与结算规则是同一个矩阵的两个面（都由"渠道 × 业务"决定）——两者应当一起设计，否则会各改各的、互相不一致。
  • KOL 分销会把"授权 + 结算 + 身份"三件事同时逼上台面：渠道只有几家，KOL 可能几十上百个。

【待确认】

  • 合规 / 牌照：中日（未来中日台）两侧是否有支付/资金资质约束？
  • 支付方式（微信 / 支付宝 / 信用卡 / 日本本地支付）
  • 退款 / 售后谁承担（门票酒店取消政策）
  • 给股东方（机场、佐川）的分账比例是否与普通合作方不同
