**横切件**：`综合平台API`（对外数据出口，合作方拉我们分享的数据）｜`管理端`（A 端内部后台，含渠道权限配置）

### 1.2 把业务串起来的五条关系（这才是"全貌"）

| 关系 | 内容 | 现在有载体吗 |
|---|---|---|
| **R1 客群 → 业务** | 谁买：C 端旅客 / B 端日本商户 / 在日华人 | 部分（v1 靠颜色+形状暗示） |
| **R2 业务 → 供给** | 谁供：自建（行前购、空手行）/ 合作（JTR、Jalan、fintech、租车、和光百货） | **几乎没有** |
| **R3 业务 → 系统** | 谁承载：Portal / API / 商户平台 / 管理端 | 部分（v1 有颜色，无连线） |
| **R4 渠道 → 业务** | 能不能拿：自有端全量；外部渠道按业务逐项授权 | **完全没有** |
| **R5 业务 → 能力** | 要用什么：交易/资金/结算/履约 全套 vs 只要前端 | 部分（v1 有"场景→服务能力"10 条线） |
| **R6 钱怎么走** | 哪些业务过我们账、怎么分账 | **完全没有** |

**【判断】** v1 图只覆盖了 R1、R3、R5 的一半，缺 R2、R4、R6 —— 而这三条恰好是"撮合型业务"的命门。

### 1.3 交易链路三档（决定每块业务要用哪些能力）

| 档位 | 业务 | 需要的自建能力 |
|---|---|---|
| **全链路** | 行前购、空手行 | 交易、支付、资金、结算、履约、风控 —— 全套 |
| **半链路** | 门票、酒店、VIP | 前台展示、营销、渠道授权、订单转接；**结算在对方** |
| **零链路** | 留学缴费 | **一个跳转。什么都不用** |
| **无交易** | 行程规划 | 大模型 + 数据 + 供给接入（用于嵌入推荐） |

**【判断】** 这一档位划分应该是架构的**第一维度**——因为它直接决定"这块业务要不要进我们的交易/资金/结算链路"，比"它属于哪个场景"重要得多。

## 第二部分 · 系统现状盘点

### 2.1 系统清单（按性质分，不按"层"分）

| 系统 | 归属 | 性质 | 服务谁 | 状态 |
|---|---|---|---|---|
| `综合平台Portal` | 我们 | **自建**（web 前台，PC + H5） | C 端旅客 | 在跑 |
| `综合平台API` | 我们 | **自建**（对外数据出口） | 外部合作方 | 在跑 |
| `商户平台` | 我们 | **自建** | B 端日本商户 | 在跑（线上销售不看好） |
| `管理端` | 我们 | **自建**（内部后台） | A 端 = 我们自己 | 在跑 |
| 行前购 | 我们 | **自建业务系统** | C 端旅客 | 在跑 |
| 空手行 | 我们 | **自建业务系统** | C 端旅客 | 在跑 |
| `佐川物流` | **合作方** | **对接/合作方系统** | 履约 | 在跑 |
| JTR / Jalan | **合作方** | **对接**（门票、酒店供给） | C 端旅客 | 在跑 |
| fintech | **合作方** | **跳转链接** | 留学生 | 在跑 |
| 线下租车公司 | **合作方** | **线下对接** | C 端旅客 | 未上线 |

**【判断】** v1 图把 `佐川物流` 和自建业务系统并排放在"应用系统"层，是**最需要修正的一处**——它让"我们自己的系统边界"变得不可读。一个 CTO 看图时最该一眼看清的，恰恰是"哪些是我们的、哪些是别人的"。

### 2.2 能力层盘点

| 层 | 格子 | 我的盘点 |
|---|---|---|
| 服务能力（9） | 交易、物流、导购、优惠券、租车、预约、留学缴费、门票、退税 | **只有交易、物流、优惠券、退税 像自建能力**；门票 ≈ 对接 JTR、酒店/留学缴费 ≈ 对接+挂链、租车 = 线下对接、导购 = 模型调用、预约 = 规划中 |
| 基础能力（11） | 会员、交易、营销、履约、资金、结算、风控、商品、库存、大模型、数据资产 | 前 9 个是**交易域原子能力**；`大模型` 是**技术底座**；`数据资产` 是**数据底座** —— 三类混在一层 |

**【事实】** CTO 已确认：`在线交易` 作为业务指行前购的线上下单，而"在线交易能力"是平台的**基础能力**——即 `SC-01 交易服务` 与 `BA-02 交易服务` **是同一个东西**。

**【判断】** "服务能力"这一层现在的实际角色是**"业务 → 能力"的映射表**，不是独立的能力抽象。它有两种可能的未来：① 承认它是映射层（那就叫"业务支撑关系"，不要叫能力）；② 真正按"可复用能力"重划（那它会与基础能力合并重排）。

## 第三部分 · 诊断：边界与缺口

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **D1** | **"业务场景"层混装四类东西** | 真业务（门票/酒店）、自营服务（行前购/空手行）、功能（行程规划）、内部管理（渠道权限） | 分层口径失效，越拆越乱 |
| **D2** | **服务能力层与基础能力层重复** | `交易服务` 两层同名同物 | 同一件事两处维护 |
| **D3** | **部分"服务能力"实质是对接关系** | 门票≈JTR、留学缴费≈挂链 | 误以为我们有这些能力，实际依赖对方 |
| **D4** | **合作方被画成自有系统** | `佐川物流` 在"应用系统"层 | 自有系统边界不可读 |
| **D5** | **渠道授权（渠道×业务）无载体** | 携程拿不到酒店、东航可以 | 一等关系缺失，无法核对 |
| **D6** | **资金与结算流向不可见** | 门票/酒店/VIP 是否分账未知 | 结算服务可能被设计错 |
| **D7** | **业务无系统支撑** | 酒店预订在 v1 图里连格子都没有 | 业务已长出来，架构没跟上 |
| **D8** | **基础能力层混了三类** | 交易域 9 个 + 技术底座 1 + 数据底座 1 | 层内不同质，看不出依赖顺序 |
| **D9** | **状态维度缺失** | 未上线的租车、规划中的预约、浅实现的行程规划，与在跑业务长得一样 | 内外沟通时容易被误读为"已有" |
| **D10** | **单点供给依赖** | 空手行→佐川；门票→JTR；酒店→Jalan；留学缴费→fintech | 合作方变化直接冲击业务 |

## 第四部分 · 规划与设计【建议】

> ⚠️ **本部分已被 `docs/平台大框架.md` 取代（2026-09-28 定稿）。**
> 本部分是在**信息还不完整时**写的分层主张（当时还不知道"不做自有流量、靠渠道分发""组织里有社媒 + KOL 这条线""台湾站独立建站"等关键事实）。CTO 与我在 2026-09-28 讨论后确认的大框架是**「分发面三条线 + 平台中枢（六职能 + 三横切）+ 供给面 + 底座」**，见 `docs/平台大框架.md`。
> **保留本部分仅作过程记录，不要按它施工。**

> 以下是设计主张，供讨论。核心思路：**把"撮合型业务"的三条命门关系（供给、渠道授权、资金）显式成结构，而不是继续在原有五层里往细拆。**

### 4.1 分层建议

```
┌─ 触达层 ────────────────────────────────────────────────┐
│  自有端：WEB / APP / 微信小程序                          │
│  外部渠道：携程 / 东航 / 其它渠道 / AI 渠道（只导流）      │
│  对外出口：综合平台 API（我们 → 合作方的数据分享）         │
└─────────────────────────────────────────────────────────┘
┌─ 业务层（按业务线切，不按场景平铺）──────────────────────┐
│  自营闭环：行前购 ｜ 空手行                              │
│  合作分销：门票 ｜ 酒店 ｜ VIP ｜ 租·包车                │
│  能力输出：退税 ｜ 优惠券 ｜（预约·预定）                 │
│  引流合作：留学缴费（挂链）                              │
│  平台功能：行程规划（生成式入口）                         │
└─────────────────────────────────────────────────────────┘
┌─ 供给与集成层【新增】───────────────────────────────────┐
│  合作方对接：佐川（履约）｜ JTR（门票）｜ Jalan（酒店）    │
│              fintech（汇款）｜ 租车公司 ｜ 和光百货/fufu   │
│  集成方式标注：API / 跳转链接 / 线下                     │
└─────────────────────────────────────────────────────────┘
┌─ 能力层（区分"自建 / 对接"）─────────────────────────────┐
│  自建：交易 ｜ 支付 ｜ 资金 ｜ 结算 ｜ 履约 ｜ 优惠券      │
│        退税 ｜ 会员 ｜ 风控 ｜ 商品 ｜ 库存              │
│  对接：物流（佐川）｜ 门票（JTR）｜ 酒店（Jalan）          │
└─────────────────────────────────────────────────────────┘
┌─ 底座 ──────────────────────────────────────────────────┐
│  大模型 ｜ 数据资产                                      │
└─────────────────────────────────────────────────────────┘

横切（用矩阵表达，不画成层）：
  ① 渠道 × 业务 授权矩阵      ② 业务 × 资金/结算 过账关系
  ③ 业务 × 能力 依赖矩阵      ④ 供给方 × 集成方式 清单
```

**关键改动**：
1. **新增"供给与集成层"** —— 合作方从"应用系统"里解放出来。以后每接一个合作方，落的是这一层，不再污染自有系统边界。
2. **业务层按业务线切**，不再按"11 个场景"平铺；"功能"（行程规划）和"内部管理"（渠道权限）从业务层移出。
3. **能力层标注自建/对接** —— 避免"我们以为有、其实是别人的"。
4. **底座只剩大模型 + 数据资产** —— 与交易域原子能力分层。
5. **渠道授权与资金流向用矩阵表达** —— 不画成层，因为它们是关系不是结构。

### 4.2 业务分级与投入建议

| 层级 | 业务 | 建议投入 |
|---|---|---|
| **深做（自建能力）** | 行前购、空手行 | 闭环在自己手里，交易/履约/结算全套要走通；这是护城河 |
| **产品化（B 端能力）** | 退税、优惠券、预约·预定 | 输出给日本商户，做标准能力 + 商户自助配置 |
| **做薄（集成）** | 门票、酒店、VIP、租·包车 | 对接 + 分成规则 + 渠道授权，不重投入自建 |
| **零投入（挂链）** | 留学缴费 | 维护链接即可，别自建 |
| **观察** | 行程规划 | 定位是"入口/前台"，值得做，但要等 JTR/Jalan 打通后才成立 |

**【判断】** 这个分级的意义在于：**别把"集成型业务"当"自建业务"设计**。门票、酒店如果按自建供给来设计交易链路，会做出一堆用不上的能力。

### 4.3 给 CTO 的五个决策建议

| # | 建议 | 理由 |
|---|---|---|
| **1** | 把"供给与集成"显式成一层，并给每个合作方标注集成方式（API / 跳转 / 线下） | 10 条诊断里 D3、D4、D10 都源于此；不解决就会反复踩 |
| **2** | 渠道授权做成**可配置矩阵**（渠道 × 业务），不要靠人管 | 携程/东航这类差异化只会越来越多；AI 渠道进来后外部渠道数量还会涨 |
| **3** | 能力层去重并定性：`交易服务` 只留一处；明确"服务能力"是映射层还是能力层 | 否则两层永远对不齐，也没法评估复用度 |
| **4** | **先弄清哪些业务过我们账、怎么分账**（门票/酒店/VIP） | 直接决定资金与结算服务的设计；这是当前最大的信息缺口 |
| **5** | 判定 `数据资产` 是自建积累还是合作方提供 | 决定护城河在哪、技术投入方向对不对 |
