## 一、本质

**BilionPass 不是"按层堆功能的系统"，而是把「本地服务供给」做成可被 B 端渠道接入的解决方案，同时面向旅客提供本地服务。**

- 不做自有流量采买，**主分发靠 B 端大渠道**（携程、东航）
- 向渠道提供具体本地服务方案，例如 Jalan 酒店、Canlead 租车等供给接入
- 自己**主动获客**的部分是社媒 + KOL（第三条线）
- 自有端承担**渠道覆盖不到的客群**（非中国 / 全球游客）
- **业务不是一层，而是"实例"**：每个业务 = 某供给 + 中枢某几项职能 + 某条分发线

## 三、分发面（三条线，定稿）

| 线 | 覆盖客群 | 接入形态 | 现状 |
|---|---|---|---|
| **① 外部渠道** | 中国客群 | API 对接（携程·空手行）｜ H5 嵌入（东航·空手行） | 在跑 |
| **② 自有端** | 非中国 / 全球客群 | bilionpass.com · APP · 小程序 | 在跑（行前购自营商城） |
| **③ 社媒与 KOL** | 内容种草 + 分销 | 自营社媒账号 ｜ KOL 分销 | 规划中（部门已存在） |

**要点**：同一业务可走**多条线**（空手行 = 携程 API + 东航 H5 + 自有端），因此"分发线 × 业务"是**多对多** → 用关系矩阵表达，**不占骨架中的层**。

**一条通则（已确认）**：**接入方式 → 成交位置 → 资金流向 → 结算复杂度**

| 集成形态 | 谁成交 | 钱怎么走 |
|---|---|---|
| **API 对接** | 渠道页面成交 | 渠道收款 → 按周期结算给我们 |
| **H5 嵌入** | 我们的页面成交 | 钱直接到我们账 |

## 四、平台中枢

### 业务职能

| # | 职能 | 说明 | 现状 |
|---|---|---|---|
| ① | **商品与库存** | 把供给方货源统一成可售商品；**两种权威源**：自有商品 / 合作商品（镜像） | 商品在跑；库存**规划中** |
| ② | **订单与履约编排** | 接单 → 派履约 → 追踪状态 | 订单在跑；履约**仅空手行**（佐川） |
| ③ | **资金与结算** | 代收 → 分账 → 对账 → KOL 分佣。**主动脉** | 资金在跑；结算**手工** |
| ④ | **分发与授权** | 渠道 × 业务：谁能卖什么、怎么结算；KOL 分销与归因 | 渠道对接在跑；**授权未系统化** |
| ⑤ | **商户能力输出** | 退税 · 优惠券 · 会员 ·（预约·预定） | 优惠券**已开发**；退税**在开发**；会员 case by case |
| ⑥ | **内容与获客** | 社媒账号运营 · KOL 内容合作 · GEO / AI 推广 | **规划中** |

### 横切（贯穿全部职能）

| # | 横切 | 为什么必须显式 | 现状 |
|---|---|---|---|
| ⑦ | **风控与合规** | 每笔交易、每次分账、每个 KOL 分佣都要过的一道闸；不显式写出就永远被跳过 | **无** |
| ⑧ | **账号与权限** | 有 C / B / A / KOL 四类主体；KOL 分销必须把订单绑到具体 KOL → 没统一身份就没有归因 | 部分（三端有账号，KOL 无） |
| ⑨ | **主数据** | 商品存在"自有 vs 合作镜像"两种权威源 → 没有统一主数据，聚合会各接各的、越接越乱 | 未定义 |

## 七、与 v1 五层图的对应关系

| v1 的层 | 在大框架里的位置 |
|---|---|
| 入口层 | **分发面**（渠道线 + 自有端线；AI 渠道不在入口，属⑥内容与获客） |
| 应用系统层 | **被拆解**：业务系统 → 业务实例；三端前台（Portal / 商户平台 / 管理端）→ 分发面与中枢；合作方系统（佐川）→ **供给面** |
| 业务场景层 | **不再是层**：业务 = 实例，用关系矩阵表达 |
| 服务能力层 | **取消**：并入中枢职能 |
| 基础能力层 | 中枢的执行能力 + 横切（风控/账号/主数据）+ 底座 |

## 八、由框架直接推出的判断

1. **① 商品与库存聚合、④ 分发与授权是可复用资产** —— 因为**每个市场都要接渠道、接供给**。② ③ ⑤ 是跟着业务走的。
2. **台湾站独立建站**，所以跨市场可复用的是"接渠道/接供给"的**方法与组件**，不是平台本身。
3. **KOL 分销**把"授权 + 结算 + 身份"三件事逼成必须先系统化（渠道只有几家，KOL 可能几十上百）。
4. **风控与合规是横切**，必须从设计一开始就穿进去，不能等"以后补"。
5. **自有端与渠道按客群互补** —— 自有端不是"要不要做"的问题，而是"服务另一批客群"的问题。
