04 ToB 渠道及开放平台

开放平台是建议规划，不是已建设模块。已发生的接入按成交和资金分开，不按页面轻重合并。

链接跳转合作方成交，资金不经过我方。现有事实：留学缴费跳转 fintech。
H5 嵌入我方页面成交，资金到我方。现有事实：东航空手行 H5。
API 对接渠道侧成交，渠道收款后按周期结算。现有事实：携程空手行 API。

目录、授权、差异化定价、佣金和结算是开放平台的规划能力。渠道关系按渠道 × 内容 × 形态记录。商户平台是日本本地商户的能力出口，不并入开放平台。

退税

开发阶段

把商户办理退税、海关确认、商户全额付款、到账核验和游客出款串成一条可对账的独立业务链路。

BilionPass 商户平台退税服务

项目目标

按已确认的 12 步流程完成退税业务，不把退税混入交易退款流程。

当前内容

  • 业务流程已确认，项目仍在开发。
  • 当前任务计划目标为 2026 年 12 月上线。
  • 国税厅接口、商户打款记录获取方式、转账网关接口和付款时限尚待落实。
  • 示例口径：退税额 1,000，服务费 150，游客实收 850。

项目范围

  • 店员登记、平台建立退税业务单、游客确认资料与收款账户。
  • 向国税厅报送购买记录，取得游客出境时的海关确认结果。
  • 通知商户财务付款，核对退税全额实际到账。
  • 保留服务费，将游客应收金额划入转账网关并反馈游客到账结果。

关联关系

外部依赖

国税厅海关确认结果商户财务我方指定收款账户转账网关

周期产出

  • 退税业务单与状态流转
  • 付款清单和到账核验
  • 游客出款指令与结果反馈
  • 退税全链路对账

已确认决策

  • 退税是独立业务；退款是交易取消或售后的逆向环节。
  • 商户先向我方账户支付退税全额，平台核对实际到账后再出款。

待确认事项

  • 国税厅具体接口与接入方式。
  • 商户打款记录及银行到账信息的获取方式。
  • 转账网关资金划入、出款和结果查询接口。
  • 商户付款时限。

验收口径

  • 能区分报送受理、海关确认、商户打款记录、实际到账和游客到账。
  • 失败、处理中和重试不会造成重复付款或重复出款。
  • 退税额、服务费、游客实收和资金流水可以逐笔对账。

退税

开发阶段 · 12 月上线计划

游客含税购物、出境接受海关核验；商户向我们支付退税全额，平台核对到账后扣除服务费，通过转账网关向游客出款。

日本本地商户与符合退税条件的游客

01

当前事实

  • 进度：退税属于商户端服务，目前正在开发，尚未上线。
  • 已确认金额：示例为未税商品价 10,000、税额 1,000，游客向商户支付 11,000。商户支付退税全额 1,000，平台收取 15% 服务费 150，游客实收 850。
  • 信息上报与海关核验：店员登记、平台建单、游客确认后，平台向国税厅报送购买记录；游客出境接受海关核验，平台取得确认结果后生成商户付款清单。
  • 商户付款：商户财务核对清单，将退税全额汇入我们公司指定的退税收款账户，并提供可关联清单或批次的打款记录。
  • 游客出款：平台匹配打款记录、付款清单和实际到账金额。核对到账后保留服务费，将游客应收款划入转账网关的出款账户并发送出款明细，网关向游客指定账户转账。
  • 业务边界：退税以独立业务单记录退税额、服务费、游客实收金额和办理进度。退款是原交易的取消或售后环节，两者的业务规则与流程分别管理。

逻辑子能力

品牌与类目维护
商品运营维护品牌、分类树、类目属性及必填项，停用分类前检查已有商品。
输出可引用的品牌 ID、类目 ID 和属性模板；类目调整不改写历史订单。
商品与规格编辑
建立商品档案，编辑多语言名称、图片、属性、规格和服务适用条件，完成字段校验后发布。
商品与可交易规格分开；机场实物规格、票种、房型通过业务扩展保留差异。
供给接入与映射
适配器导入外部商品，运营处理未匹配、重复映射和供给停用。
按产品、供给方、外部编码维护映射；同一商品允许关联多条供给报价。
报价与发布
管理供给报价来源、币种、适用日期和有效期，校验后发布指定版本。
仅提供基础报价及来源；酒店实时询价由酒店业务适配器获取，营销算优惠，订单固化最终金额。
查询与分发
向商城、业务 API 和运营台返回商品详情、规格和发布版本。
查询必须带产品与渠道上下文；渠道可售权限由授权能力裁定，发布不意味着所有渠道可售。

核心对象与数据边界

品牌 / 类目
brandId、categoryId、parentId、属性模板版本
一个类目定义一组商品属性约束；品牌归属与分类独立，类目树不能形成循环。
商品 / 规格
productId、variantId、产品归属、类型、版本、发布状态
商品包含多个规格；订单引用规格与版本。房型、票种等专用字段由业务维护。
供给映射 / 报价
supplierId、externalCode、variantId、币种、有效期、源版本
供给编码只在对应合作方内唯一；币种和日期条件不可在映射中丢失。

主要调用契约

保存 / 发布商品｜运营台 → 商品域
商品 ID、预期版本、品牌类目、规格及发布范围
返回新版本或字段冲突；引用和必填项通过后才切换已发布版本。
导入供给｜业务适配器 → 商品域
供给方、外部编码、来源版本、规格与报价
返回映射 ID 和处理结果；重复版本不重复建商品，旧版本不能覆盖新版本。
查询可售定义｜业务应用 / 订单 → 商品域
产品、渠道、规格 ID、日期与语言
返回发布版本、基础报价、有效条件；价格过期需重新询价，库存另查库存域。

状态流转

  • 草稿 → 校验通过 → 已发布 → 已下架 / 已停用。变更先产生新草稿，发布时切换生效版本。
  • 下架阻止新增交易，但保留商品标识、订单快照和售后查询；供给失效与整件商品下架分别处理。

典型协作场景

事件与异步协作

  • 商品发布或状态变化在版本生效后发出，携带 productId、variantId、产品归属和版本。
  • 搜索与展示视图异步更新；下单校验读取权威版本，不能只依赖缓存页面的上架状态。

失败、补偿与边界

  • 外部品牌或类目不匹配：导入暂存区，记录原因供运营修正，不能生成缺少关键属性的可售商品。
  • 并发编辑：按预期版本拒绝覆盖并返回冲突字段；禁止后提交的旧页面静默覆盖。
  • 外部报价过期或接口不可用：返回不可报价及原因；是否允许保留展示由业务决定，不能按旧价自动成交。

验收口径

  • 关西、JTR 和 Jalan 的同名外部编码不会串供给。
  • 修改商品名称、规格或价格后，旧订单仍能还原原成交内容。
  • 下架、价格失效、越权渠道请求均能返回可解释的拒绝结果。

仍需决策

  • 产品归属及 ID 命名空间如何与现有商品数据兼容；先迁移哪些对象。
  • 酒店、门票哪些报价必须实时取得，哪些允许带有效期缓存；基础售价维护入口由谁使用。

库存域

规划阶段 · 周期 2 · 可售与同步

管理前台可售库存，并同步外部系统的库存与可售状态。

平台各产品与业务

01

当前事实

  • 行前购已通过机场 API 同步商品与库存；面向门票、酒店及其他外部供给的通用库存能力仍在规划。
  • 数据归属：可售库存、库存来源映射、同步状态、预占与释放结果
02

架构蓝图（建议规划）

可售视图服务查询，库存预占服务下单，外部同步负责校准来源事实。必须先区分“平台能锁库存”和“只能向供给方询量”，再决定成交方式。

逻辑子能力

库存来源与能力配置
登记每个机场、JTR、Jalan 的查询、预占、扣减、释放能力及同步方式。
按供给方实际接口启用能力；没有预占接口时不得向业务返回已锁定。
可售量查询
按商品、地点、日期、场次或入住离店区间查询可售状态。
返回数量或可售布尔值、来源时间和有效期；区分售罄、过期、未知。
同步与差异处理
接收全量、增量或回调数据，记录游标和最近成功时间；运营查询失步商品。
更新来源快照并标出差异；外部剩余量是否已扣锁定量必须明确。
库存预占与释放
按订单请求预占指定数量，订单确认后提交，取消或到期后释放。
记录本地与外部预占号；只读库存模式返回需供给方确认，不伪造扣减。

核心对象与数据边界

库存来源 / 库存键
产品、supplierId、variantId、地点、日期 / 场次
库存归属于明确来源；酒店按入住区间逐日校验，不能只比较第一晚。
来源快照
来源数量、观测时间、源版本、同步游标、可售语义
权威来自供给方；平台自管配额与外部快照分开，不能简单相加。
预占记录
reservationId、orderId、库存键、数量、expiresAt、外部预占号
一笔订单可有多个库存项；记录逐项成功与失败，便于补偿释放。

主要调用契约

查询可售｜前台 / 订单 → 库存域
库存键、数量、日期区间
返回可售 / 不可售 / 未知、有效期与来源时间；查询结果本身不构成预占。
预占｜订单 → 库存域
业务请求号、订单号、库存项和失效时间
返回逐项预占结果或待外部确认；同一请求不能重复锁量。
确认 / 释放｜订单 → 库存域
预占号、动作及幂等号
返回最终状态或处理中；超时先查原预占，不重复扣减。

状态流转

  • 同步：正常 → 超过有效期 → 待刷新 / 异常；恢复后只接受比当前更新的来源版本。
  • 预占：请求中 → 已预占 → 已确认；已预占也可转释放中 → 已释放 / 已过期。结果未知单列，等待查询。

典型协作场景

事件与异步协作

  • 可售量变化提供库存键、来源版本、观测时间与有效期，用于刷新商品展示。
  • 预占成功、释放完成关联原订单和预占号；重复消息不能再次增加或扣减数量。

失败、补偿与边界

  • 只有查询接口：下单后由供给方确认可售；拒单由业务触发取消及已收款退款，不能以缓存可售量保证成交。
  • 乱序快照或重复回调：依据来源版本去重；无来源版本时按接口约定串行采集并安排复核。
  • 部分预占成功：释放已成功项并记录补偿状态；释放成功必须有外部确认或本地自管库存的有效事务结果。

验收口径

  • 并发预占自管配额时不产生负库存；外部配额按外部结果认定。
  • 同步中断时前台能区分未知与售罄，并按业务策略停止确认新订单。
  • 重复释放、过期释放和延迟回调不会把库存加回两次。

仍需决策

  • 逐家确认库存语义、刷新时效、接口限流，以及外部数量是否包含预占。
  • 无预占能力时，各业务采用先确认后收款还是先收款后确认；拒单补偿由谁执行。

订单域

运行中 · 周期 1 · 基础模型

专门管理订单，记录从下单到关闭的业务交易事实。

平台各产品与业务

01

当前事实

  • 空手行等交易能力已在运行；行前购、门票、酒店等产品的订单边界与共用字段仍需分别确认。
  • 数据归属：订单主单、订单明细、商品与价格快照、订单状态、业务单关联
02

架构蓝图（建议规划）

订单是交易承诺与成交快照的权威记录。订单状态、支付状态、履约状态分别建模，由业务确认条件驱动协作，不用一个“成功”覆盖所有阶段。

逻辑子能力

结算试算与订单创建
提交商品、旅客、渠道和优惠意图，校验报价、库存条件及业务可下单规则。
输出订单号和不可变成交快照；试算有有效期，创建订单须再次校验。
订单生命周期
受理确认、取消、关闭、完结请求，记录状态原因及来源业务单。
业务决定何时确认；付款成功、合作方接单和交付完成分别记录。
关联与查询
前台查看自己的订单，客服按产品、会员、合作方单号查询订单进度。
一个交易订单可关联多个履约单、收付指令和售后单；数据按产品归属隔离。
取消与售后
受理整单或明细级售后，调用业务退改规则计算允许范围和退款金额。
协调库存、营销、履约和资金处理；退税单由独立退税业务维护。

核心对象与数据边界

订单 / 明细
orderId、产品、渠道、memberId、variantId、数量、业务单号
订单持有明细和状态版本，业务扩展通过业务单关联；不复制整个酒店或物流业务模型。
成交快照
报价版本、币种、原价、优惠、应付、费用及规则版本
订单确认后不随商品或营销规则变化重算；调整通过售后明细记录。
状态 / 售后单
订单状态、支付状态、履约摘要、afterSalesId、退款引用
分别推进状态；售后批准不等于退款成功，部分退款按明细累计校验。

主要调用契约

创建订单｜业务应用 → 订单域
产品、渠道、幂等号、会员、商品数量、报价与优惠凭据
返回同一个订单号或明确拒绝原因；同请求不同内容必须报冲突。
申请取消 / 售后｜旅客或客服 → 业务规则 → 订单域
订单版本、明细、原因、业务审核结果
返回申请号和处理中状态；资金执行异步回传，前台不能提前显示退款完成。
结果回传｜资金 / 履约 → 订单域
事件 ID、业务单引用、结果版本和凭据
仅更新对应维度；延迟旧事件不能让订单从完结倒退到处理中。

状态流转

  • 订单：待确认 → 已确认 → 已完结；可取消阶段进入取消中 → 已取消。部分交付与售后单独记录。
  • 支付：未收款 / 处理中 / 已收款 / 部分退款 / 全额退款。履约摘要：未开始 / 处理中 / 部分完成 / 已完成 / 异常。

典型协作场景

事件与异步协作

  • 订单创建、确认、取消事件在订单事务提交后发出，携带订单版本、产品及业务引用。
  • 资金与履约结果由订单消费；消费者对 eventId 去重，失败重试不再次生成交易或出款。

失败、补偿与边界

  • 提交后网络超时：按原幂等号查询结果，禁止用户刷新后生成重复订单。
  • 库存或优惠确认失败：保留订单处理状态并补偿释放已成功资源；不得把本地回滚当作外部操作已撤销。
  • 取消与付款并发：按订单版本裁定；取消后才收到已收款凭据时进入待退款处理，不丢弃资金事实。

验收口径

  • 重复下单只产生一笔订单，报价变更后可追溯原成交金额。
  • 部分退款累计金额不超出可退金额，各退款都有原订单和售后依据。
  • 取消失败、晚到支付和部分履约均有明确状态及后续处理入口。

仍需决策

  • 各业务何时算订单确认、是否允许部分履约及部分取消；收款触发点分别是什么。
  • 现有订单号与共享模型如何兼容；首期复用哪条业务，哪些保留独立实现。

履约域

规划阶段 · 周期 2 · 可售与同步

专门管理成交后的交付过程、结果和异常。

平台各产品与业务

01

当前事实

  • 空手行与佐川物流履约 API 已打通；通用履约能力仍在规划。
  • 数据归属：履约单、交付任务、履约状态、完成凭据、异常与重试记录
02

架构蓝图（建议规划）

履约域拥有交付任务、执行记录与凭据，业务适配器负责佐川、机场、票务和酒店的专有协议。共同状态只用于汇总，不能抹掉业务完成条件。

逻辑子能力

任务拆分与派发
根据业务交付规则将订单明细转成履约任务，指定供给方和目标服务。
支持一个订单对应多项任务；是否拆单由业务规则决定。
合作方接入
调用业务适配器下发物流单、预订单或出票请求，关联外部履约号。
区分请求受理、业务确认和最终交付；机场取货与佐川配送分别保留原始状态。
进度与凭据
消费合作方回调或查询结果，对外提供统一进度与原始凭据查询。
完成记录必须指向具体明细、数量和业务认可的凭据。
异常处理台
运营查询超时、拒单、交付失败，执行查单、补正、重试或申请撤销。
保留每次操作原因与结果；资金退款仍由业务售后流程发起。

核心对象与数据边界

履约单 / 任务
fulfillmentId、orderId、orderItemId、任务类型、数量、供给方
订单可有多笔履约单；任务状态独立后再汇总订单履约摘要。
外部执行记录
externalId、请求号、尝试号、原始状态、结果版本
每次尝试关联原任务；新尝试前必须确认上一笔外部执行结果。
交付凭据 / 异常
凭据类型、来源、取得时间、异常原因、处理责任人

会员 / 身份绑定

等级 / 权益

积分账户 / 流水
accountId、memberId、积分类型、可用 / 冻结、业务引用
账户范围与现有实现保持一致；流水保留到期和冲正关系，不直接改历史余额记录。

主要调用契约

解析身份｜各产品 → 会员域

memberId、权益范围、查询时间

积分操作｜营销 / 业务 → 会员域

  • 积分使用：可用 → 冻结 → 已扣减，失败则解冻；退款后的返还或冲正按已确认积分规则执行。实际状态名称对照现有接口。

架构蓝图（建议规划）

逻辑子能力

活动和券码配置

售后处理与查询

原订单、退款明细、取消依据

资金域

规划阶段 · 周期 4 · 资金闭环

管理业务收付款指令、账户流转、到账确认和资金执行结果。

平台各产品与业务

01

当前事实

  • 资金能力处于规划阶段；退税已确认需要商户全额付款、实际到账核验和转账网关出款，相关接口尚待完成。
  • 数据归属：收付款指令、账户路由、资金流水、到账状态、执行回执
02

架构蓝图（建议规划）

业务提供应收应付依据，资金域负责执行、实际到账核验和流水记录。退款、退税出款、网关资金划入是不同指令，必须分别取得结果。

逻辑子能力

资金指令受理
业务提交收款、退款、转账意图，校验业务单、金额币种、账户与幂等号。
返回资金指令号；业务资格和金额算法仍归原业务。
账户与渠道路由
按产品、法人主体、币种及收付类型选择已配置收款账户或出款渠道。
公司银行账户与网关出款账户独立登记；账户凭据由安全底座保管。
实际到账匹配
接入银行到账证据，按商户、清单、金额和引用匹配；差异由财务处理。
打款记录仅为匹配线索；不能直接把商户提交的凭证标作到账。
执行与结果查询
发送收付指令、验签接收结果、查询处理中任务，按实际回执推进状态。
网关资金划入和游客出款分别执行；查询原笔结果后才能决定重试。
流水与核对
按资金动作保存原始回执和账务记录，核对金额、币种、费用与业务归属。
保留不可覆盖的执行证据；更正以冲正或调整记录完成，不改历史流水。

核心对象与数据边界

账户 / 资金指令
accountId、主体、币种、instructionId、业务单类型及编号、幂等号
业务引用可指退税单而无需交易订单；每笔指令限定一种动作和币种。
到账证据 / 分配记录
银行流水号、金额、到账时间、付款人、清单与分配金额
一笔到账可匹配多张退税单，分配总额不能超出已核验到账；歧义进入人工队列。
执行尝试 / 资金流水
attemptId、渠道请求号、回执号、执行状态、费用
渠道受理、网关资金划入和游客到账是不同证据；每次重试挂在原指令。

主要调用契约

受理出款｜退税业务 → 资金域
退税单、海关确认引用、已核验收款分配、服务费及游客应收、账户
校验前置事实后返回指令；1,000 收款对应 150 留存与 850 出款，具体接口待对接落实。
匹配到账｜银行数据 / 财务 → 资金域
银行流水证据、商户、清单、金额币种
返回已匹配、部分匹配或需复核；重复银行流水不能重复入账。
查执行结果｜业务 / 结算 → 资金域
业务引用或指令号
返回受理、处理中、已到账、失败或结果未知及证据；不将受理包装为成功。

状态流转

  • 资金指令：待校验 → 待执行 → 已提交 → 处理中 → 成功 / 失败。网络超时进入结果未知，经查询后确定，不直接视为失败。
  • 退税出款门槛：海关确认 → 商户实际到账已核验 → 网关资金划入成功 → 游客出款；每步保留独立记录。

典型协作场景

事件与异步协作

  • FundsReceived 只在实际到账核验和分配记录提交后发出；PayoutCompleted 必须有游客出款最终成功的可靠证据。
  • 事件带业务单类型、指令号、金额币种及凭据引用，禁止携带完整银行卡或认证凭据。

失败、补偿与边界

  • 实收 1,000、服务费 150、网关划入 850 与游客实收 850 可分别查证，不重复算作收入。

  • 银行到账数据来源、商户付款时限、网关划入和出款接口及最终成功凭据待落实。

结算域

规划阶段 · 周期 4 · 资金闭环

按合作条款计算各方应收应付，并完成账单和差异对账。

平台各产品与业务

01

当前事实

  • 当前仍以手工对账为主；渠道周期结算、供给方结算及退税服务费都需要明确结算口径。
  • 数据归属：结算规则、应结金额、账单批次、对账结果、差异处理记录
02

架构蓝图（建议规划）

结算从成交、履约与实际收付事实推导各方应收应付。规则版本、计费依据、账单明细与调整记录构成可追溯的结算链，不用付款流水代替结算规则。

逻辑子能力

合作规则维护
财务按渠道、供给方、产品、币种配置费率、计费条件、周期与生效时间。
发布前确认条款依据；5% 等初步方案不能直接启用自动结算。
费用与账单生成
读取订单明细、履约证据、优惠承担和退款，按规则生成应收应付行及批次。
每行保留规则版本、来源单据和计算过程；同一计费事实不能重复出账。
对账与差异处理
导入合作方账单，与内部应结金额和资金流水逐项匹配。
区分漏单、金额、币种、状态和到账差异；财务记录确认或调整依据。
结算确认与资金协作
财务审核账单，确认后向资金域发出对应的付款意图或收款核对请求。
账单确认、付款发起、实际结清分别记录；取消和退款形成后续调整。

核心对象与数据边界

规则版本
合作方、产品、币种、有效期、费用类型、计费触发条件
不同合作方单独维护；历史账单引用当时版本，不套用最新费率重算。
账单 / 结算明细
statementId、batchId、业务明细、应收应付方向、金额及规则引用
一个批次由多行费用构成；不同币种分别核对，不直接抵销合计。
差异 / 调整单
差异类型、原账单行、调整原因、审批记录、资金引用
确认后的账单不直接改写；退款、漏单和纠错生成关联调整。

主要调用契约

生成账单｜财务 → 结算域
合作方、结算区间、规则版本、数据截止点
返回批次号和计算摘要；重复生成复用或显式创建修订，不重复入应付。
确认 / 调整｜财务 → 结算域
账单版本、审核依据、差异处理结论
返回生效版本和审计记录；未处理差异按约定阻止确认或列为例外。
执行结算｜结算域 → 资金域
已确认账单、应付金额币种、账户、幂等引用
资金返回指令号和结果；结算据最终收付证据标记部分或全部结清。

状态流转

  • 账单：待计算 → 草稿 → 对账中 → 待确认 → 已确认；争议项保留差异，已确认账单以调整单更正。
  • 收付：未结清 → 部分结清 → 已结清。对账匹配、财务确认和实际付款不能共用一个完成状态。

典型协作场景

事件与异步协作

  • 账单确认事件携带版本、币种与应结金额，资金只对确认后的付款意图执行。
  • 资金完成与退款事件更新结清或调整状态，不能直接覆盖原账单计算结果。

失败、补偿与边界

  • 订单或履约结果迟到：按数据截止点暂存或下期调整，不能悄悄改已发账单。
  • 对方账单与实际到账不同：记录应收差异和资金差异，避免为匹配总额而删除明细。
  • 部分退款发生在结算后：基于原费用行生成调整，保留返佣和退款承担依据。

验收口径

  • 任意账单行能追溯业务单、履约依据、规则版本和收付记录。
  • 重跑同一批次不重复产生应付，已确认账单调整有独立记录。
  • 退税服务费与网关资金划转分别核对，划转不重复计费。

仍需决策

  • 各合作方的计费时点、周期、退款佣金处理、手续费承担和币种；不预设周期。
  • 财务确认、调整审核和付款执行的责任分工及首期自动化范围。

风控域

规划阶段 · 周期 5 · 风险控制

提供业务规则检查、风险识别、人工审核和处置记录。

平台各产品与业务

01

当前事实

  • 目前尚无完整风控能力；优惠滥用、异常订单、重复出款和退税审核等场景需要逐项确认。
  • 数据归属：业务风控规则、命中记录、审核任务、处置结果、风险事件
02

架构蓝图（建议规划）

风控提供带证据的业务检查结论，调用业务负责执行约束。通用风控建设虽在后续周期，防重复收付、金额上限和退税前置检查必须随相关域首期实现。

逻辑子能力

规则与版本管理
业务负责人定义触发场景、输入事实、阈值、适用范围及处置动作。
规则发布可回滚，有版本和生效记录；不先设未经确认的风险阈值。
动作前检查
订单、营销或资金提交待执行动作，返回通过、拒绝、待审核或无法判定。
结论绑定被检查的动作、金额和数据版本；事实变化后重新检查。
人工审核工作台
审核人员查看证据、补充资料、批准或拒绝，并记录原因。
待审不能等同放行；高风险操作的审核权限与业务操作权限分离。
风险事件与复核
归集规则命中、业务处置和最终结果，分析误拦截及漏拦截。
保留规则版本、证据引用和处置链；技术攻击防护仍由安全底座负责。

核心对象与数据边界

规则 / 规则集
ruleId、版本、场景、条件、动作、有效期
配置逻辑按业务审核，不由技术域自行决定风险政策。
检查请求 / 结论
decisionId、业务动作、事实版本、证据引用、有效期
同一主体不同金额或动作不能复用旧放行结论。
审核任务 / 处置
reviewId、关联检查、处理人、原因、复核记录
一次审核针对指定版本，业务变化后需新检查；全过程留痕。

主要调用契约

检查动作｜营销 / 订单 / 资金 → 风控域
动作类型、产品、主体、金额及事实引用、请求号
返回结论、命中原因、规则版本与有效期；无法判断显式返回，不默认通过。
审核｜审核人员 → 风控域
任务版本、证据、决定和原因
返回审核结果；与原动作及当前版本一致才允许业务继续。
结果反馈｜调用业务 → 风控域
decisionId、实际执行结果、补偿或投诉结果
形成处置记录供复核，不由风控直接改订单或重发付款。

状态流转

  • 检查：已受理 → 通过 / 拒绝 / 待审核 / 无法判定；结论过期或事实变化须重新检查。
  • 审核：待处理 → 处理中 → 已批准 / 已拒绝 / 待补充 → 已关闭；关闭保留原因和证据。

典型协作场景

事件与异步协作

  • 审核完成事件只表达该版本动作的决定；资金收到后仍需检查有效期、金额和原笔结果。
  • 风控不可用时由场景策略决定挂起、人工处理或其他降级；资金关键操作不默认放行。

失败、补偿与边界

  • 证据缺失或规则超时：显式返回无法判定，交人工或等待补充。
  • 审核期间金额或账户被改：原结论失效，重新发起检查，避免批准另一个动作。
  • 规则误拦截：回滚规则版本并复核受影响记录，不能批量重放原出款。

验收口径

  • 每个拒绝或待审结论均有规则版本和证据，前台或运营能理解处理原因。
  • 过期批准、重复审核回调及金额变更不能绕过关键资金检查。
  • 规则停用和服务不可用时，相关业务有可执行的处理策略。

仍需决策

  • 首批场景、判断阈值和人工审核责任由业务明确；不同场景的超时处理分别定义。
  • 现有域内防重、额度和前置条件检查哪些保持本地，哪些需要通用风控协助。
