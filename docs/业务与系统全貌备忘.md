## 一、这门生意是什么

**【事实】** BilionPass 是连接日本本地服务与 B 端渠道、旅客的服务平台，属于行云集团的日本业务线。它既面向赴日中国旅客及全球游客提供服务，也向东航、携程等 B 端渠道提供本地服务解决方案。

- **服务对象**：C 端 = 赴日中国旅客与全球游客 ｜ B 端商户 = 日本本地商户 ｜ B 端渠道 = 东航、携程等合作渠道 ｜ A 端 = 我们自己公司（内部后台）
- **地理收敛**：所有业务都围绕**日本**——合作机场是羽田、成田、关西；商户是日本本地商户；幼儿园到大学的留学汇款也是中日跨境
- **自己闭环的业务只有两块**：行前购、空手行。其余靠合作供给或能力输出

**【判断】** 平台的本质是把**日本本地供给做成可被 B 端渠道接入的服务方案，并向旅客提供服务**，同时自己牢牢握着两块闭环业务（机场免税、行李托运）。这决定了架构重心不在"自建了多少能力"，而在"**接了多少供给、做成多少渠道方案**"。

## 二、业务版图

按 CTO 给出的重要性排序（**行前购、空手行、退税、优惠券、门票、酒店、VIP** 为核心）：

| 业务 | 性质 | 谁供给 | 交易在哪闭环 | 钱过我们账 | 状态 |
|---|---|---|---|---|---|
| **行前购** | 自营服务 | 我们（+机场免税店） | **我们**：线上下单 → 离境时机场取货 | 是 | 在跑 |
| **空手行** | 自营服务 | 我们（**佐川物流**履约） | **我们**：下单 → 佐川定时送到酒店 | 是 | 在跑 |
| **退税** | 能力输出 | 我们做成能力 → 给日本商户用 | 商户侧 | 服务费形态 | 在跑 |
| **优惠券** | 能力输出 | 同上（发放 / 核销） | 商户侧 | 服务费形态 | 在跑 |
| **门票** | 合作分销 | **JTR** | **合作方** | 【待确认】 | 在跑 |
| **酒店** | 合作分销 | **Jalan** | **合作方** | 【待确认】 | 在跑 |
| **VIP** | 会员 / 高端 | **和光百货、fufu 酒店**等合作场景 | **合作方** | 【待确认】 | 在跑（已有若干场景） |
| 行程规划 | **功能**（非业务） | 我们（模型调用） | 无交易 | — | 在跑但浅 |
| 租 / 包车 | 线下业务 | 线下租车公司 | 线下 | — | **未上线**（业务量小） |
| 留学缴费 | **纯挂链** | fintech（跨境汇款） | **合作方** | **不过账** | 在跑（挂链接） |
| 预约 / 预定 | 能力输出（规划中） | 我们 → 商户平台功能 | 商户侧 | — | 规划中 |

**【事实】两个关键细节：**
- **行程规划是"功能"不是"业务"**：用户输入信息 → 调模型生成行程 → 在各节点尝试嵌入门票、酒店等供给（**未来打通 JTR / Jalan 后是这个定位**）
- **留学缴费的钱不到我们账上**：fintech 业务已成熟，我们只挂链接

**【判断】场景的"交易链路深度"分三档，这是架构里最该表达的一条：**

| 档位 | 业务 | 要用我们哪些能力 |
|---|---|---|
| **全链路** | 行前购、空手行 | 交易、支付、资金、结算、履约 —— 全套 |
| **半链路** | 门票、酒店、VIP | 前端展示与营销；履约、结算在对方 |
| **零链路** | 留学缴费 | **一个跳转，什么都不用** |

## 三、系统现状

### 三端

| 端 | 是谁 | 系统 |
|---|---|---|
| **C 端** | 赴日中国旅客 | `综合平台Portal`（**旅客 web 前台，PC + H5**）、入口层 |
| **B 端** | **日本本地商户** | `商户平台` —— 输出退税、优惠券发放/核销能力；未来加预约/预定功能（**线上销售能力不看好**） |
| **A 端** | **我们自己公司** | `管理端` —— 内部运营后台（渠道权限等配置） |

### 入口与渠道

- **自有端**：WEB、APP、微信小程序
- **外部渠道**：携程、东航、其它渠道
- **AI 渠道（豆包 / 元宝 / ChatGPT 等）**：**【事实】不是渠道，是推广手段**——做法是 **GEO（生成式引擎优化）**，即在 AI 的回答里做曝光、让 AI 推荐我们；用户被种草后**自己到自有端下单**。因此**不涉及接入、不涉及渠道授权、不涉及结算**，归"营销 / 内容与获客"。**状态：计划中**（尚未落地）。
  > ⚠️ 修正：此前记作"入口层新增 AI 渠道、只导流"，把它当成了一个渠道，归类和性质都错了。

### 平台件

| 系统 | 实际角色 |
|---|---|
| `综合平台Portal` | 给旅客看的 web 前台（PC + H5） |
| `综合平台API` | **对外数据出口**：外部合作方通过它**拉取我们分享的数据** |
| `佐川物流` | **外部合作方**（日本最大物流，对标顺丰）——v1 图里被当成"应用系统"画了 |

## 四、渠道授权机制（重要）

**【事实】** v1 图说明第 4 条"不同的渠道有不同的业务场景"**不是设想，是现行机制**：

- **自有端（WEB / APP / 小程序）：全量业务**
- **外部渠道（携程、东航、AI 渠道等）：按业务逐项授权**
- 实例：**酒店预订业务不能推给携程，但可以推给东航**

**含义**：`渠道×业务` 是架构里的**一等关系**，`渠道权限` 是 A 端的核心配置面，不是挂名格子。

> 【判断】与携程"既是渠道又是竞品"的关系，是这条规则存在的现实原因之一。

## 五、能力构成

v1 图的能力层是两层：`服务能力` 9 格 + `基础能力` 11 格。

**【判断】三个观察：**

1. **两层有重复**：`交易服务` 在两层同名同物（`SC-01` 与 `BA-02`）——CTO 已确认"在线交易能力属于平台的基础能力"，即**服务能力层的交易服务与基础能力层的交易服务是同一个东西**。
2. **部分"服务能力"实质是"对接关系"而非自建能力**：`门票服务` ≈ 对接 JTR + 分成规则、`酒店` 同理（对 Jalan）、`留学缴费服务` ≈ 挂 fintech 链接。真正自建的是交易、物流、优惠券、退税这类。
3. **基础能力层混了三类东西**：交易域原子能力（会员 / 交易 / 营销 / 履约 / 资金 / 结算 / 风控 / 商品 / 库存）、**技术底座**（大模型）、**数据底座**（数据资产）。后两个与前 9 个不同层。

## 七、v1 架构图缺了什么（这是"重新梳理"的核心结论）

**【判断】** 那张图是按"**自有系统分层**"的世界观画的，因此以下维度没有载体：

| 缺失维度 | 证据 |
|---|---|
| **供给来源**（自有 / 合作方） | 佐川、JTR、Jalan、fintech、租车公司、和光百货 —— 图上只有佐川漏出 |
| **闭环位置**（我们 / 对方 / 纯跳转） | 留学缴费只是挂链，但图上给它配了个"留学缴费服务"能力格 |
| **业务线** | 图上是 11 个"场景"平铺；酒店预订本来连格子都没有 |
| **渠道授权**（渠道 × 业务） | 图上无表达，而它是现行机制 |
| **状态**（在跑 / 未上线 / 规划中） | 租包车未上线、预约预定规划中、行程规划只是模型调用 —— 图上长得一样 |
| **客群与地理** | 全靠"退税""留学缴费"这些词猜出是日本业务 |
| **数据流向** | `综合平台API` 是"我们输出数据给合作方"，图上只有一个格子 |

并且"业务场景"这一层**混装了四类东西**：真业务（门票、酒店）、自营服务（行前购、空手行）、功能（行程规划）、内部管理（渠道权限）。

**【判断】结论**：v2 要做的不只是"把格子拆细"，而是**重新表达这些缺失的关系**——尤其是"谁供给、谁闭环、渠道能不能拿、钱过不过我们"。只在原有 5 层里往细拆，会越拆越乱。

## 九、两个用途各自要什么

### A. 给老板汇报（CTO 视角，关注整体业务 + 系统）

要回答四个问题：
1. **我们做什么生意、在哪儿做**（赴日中国旅客 × 日本本地服务）
2. **有哪几条业务线、重点在哪**（自营两块 + 能力输出两块 + 合作分销三块；重要性排序）
3. **靠谁**（佐川 / JTR / Jalan / fintech / 机场 / 渠道 —— 关键外部依赖与风险）
4. **系统撑不撑得住**（三端 + Portal/API/商户平台/管理端的现状、哪些是自建、哪些是对接、哪里有缺口）

**汇报版要克制**：一页讲清"版图 + 重点 + 依赖 + 风险"，不铺细节、不出现未确认信息。

### B. 自己梳理（对系统/业务全貌的理解 + 规划与设计）

在本文这份事实基座上，往下做三件事：
1. **全貌结构化**：业务线 × 供给方 × 闭环 × 渠道授权 × 系统 × 能力的对应关系（可查询、可核对）
2. **边界与缺口**：哪些能力是我们自建的、哪些只是对接、哪些是重复的（如两层交易服务）、哪些业务还没有系统支撑（如酒店预订原来没有格子）
3. **规划与设计**：给定"撮合 + 合作供给 + 能力输出"这个本质，系统应该怎么分层、哪些要平台化、优先级怎么排

## 十一、资金与合作方结算（2026-09-28 补充）

**【事实】资金全部走我们账：**
- **行前购、空手行的钱也走我们账**（不只是门票/酒店/VIP）
- **门票 / 酒店 / VIP 过我们账，按营业额的 5% 抽佣**（**初步方案**）
- **唯一不过账的是 `留学缴费`**（挂 fintech 链接，钱不经过我们）

**含义**：`资金服务` + `结算服务` 是**全平台统一的核心链路**，不是"自营一套、分销一套"。所有业务都是"我们代收 → 分账给供给方"。因此：
- `资金服务` 必须支持**代收代付**
- `结算服务` 必须支持**多方分账**（机场免税店、佐川、JTR、Jalan、和光百货 / fufu 等）

### 关键观察（**【判断】**，需 CTO 确认）

1. **系统件齐、能力层薄**：7 个系统件全部自研在跑，但基础能力 11 格里只有 4 格在跑。
2. **与"钱和履约"直接相关的三个环节恰恰是规划中**：`结算`（分账给供给方）、`履约`（状态跟踪）、`风控`。而业务**已经在**代收全款、按合作方分账、由佐川履约、处理支付。
3. **由此推论**：这些环节目前**靠人工流程或外部系统兜着**（Excel 对账？佐川自己的系统？）——**这是当前最该确认的一条**。若成立，意味着"业务规模一大就会卡住"，也意味着系统建设的优先级应该在这里，而不在"把能力图拆得更细"。
4. `商品` 在跑、`库存` 规划中：与"商品库存数据从免税店接口同步"这个事实放在一起看，需要确认库存到底谁在管。

### 诊断结论（**【事实 + 已确认】**）

上面第 3 条的推论已由 CTO 确认，实际状况如下：

| 优先级 | 环节 | 现状 | 后果 |
|---|---|---|---|
| **1** | **结算** | **手工对账** | 全业务过账 + 多分账对象（机场、佐川、JTR、Jalan、和光百货）+ 多规则（门票酒店 5% 佣金、退税收 15% 手续费）+ 跨中日两地资金，**全靠手工**。业务量一涨即卡死；差错直接是钱 |
| **2** | **风控** | **无** | 代收全款 + 手工对账 + 零风控三重叠加：支付风险、退款欺诈、渠道套利、对账差错**无任何系统兜底** |
| **3** | **履约** | **仅空手行与佐川系统对接打通（线上在跑）** | 单点已通；但通用履约能力（服务履约 / 其它履约）不存在 → 每新增一个需履约的业务（租车、预约核销、门票核销）都要重新接一次 |

**当前说明**：本文曾记录过结算、风控、履约的先后讨论；当前文档不将其呈现为已确定的建设优先级。现状仍是：结算手工对账、风控尚未建设、履约目前仅空手行与佐川系统打通。

**总结论**：**业务侧已经跑起来、系统件也已齐备，但"钱怎么分、风险怎么控、履约怎么通用化"这三件事都还没有系统。** 而这三件恰是平台型业务最容易在规模上翻车之处。

**对"细划架构图"这件事的含义**：细划解决的是**讲清楚**，而当前真实缺口是**跑得住**——两者的优先级需要显式比较，不应默认"先把图拆细"。

> *"我们对接缝，借助本地的服务供给来丰富渠道侧的服务内容。**我们更想做的是做好渠道侧的对接，而不是自己去做推广**。"*

**含义**：BilionPass **不以自有流量为主**，而是把**本地服务供给**整合后接进**携程、东航**这类已有流量的渠道。自有站（bilionpass.com / APP / 小程序）是辅助阵地。

### 13.3 一条通则（**CTO 已确认**）

**接入方式 → 成交位置 → 资金流向 → 结算复杂度**

| 集成形态 | 谁成交 | 钱怎么走 |
|---|---|---|
| **API 对接** | 渠道页面成交 | **渠道收款 → 按周期结算给我们** |
| **H5 嵌入** | **我们的页面成交** | **钱直接到我们账** |

**因此"资金模式 C（两种都有）"不是随意混用，而是由集成形态决定的。**

**结算的完整复杂度**（第一痛点的真实规模）：

- **对手方**：渠道（携程/东航/…）+ 供给方（机场、佐川、JTR、Jalan、Canlead…）
- **方向**：对渠道**可能收也可能付**（有的渠道结算给我们，有的我们付佣金）；对供给方是**付**
- **规则**：随"渠道 × 业务"而变（5% 佣金、退税 15% 手续费…）
- **地域**：跨中日（未来中日台三地）货币与合规
- **现状**：**全靠手工对账**

> **【判断】** 渠道授权与结算规则**都是"渠道 × 业务"的函数** —— 同一矩阵的两个面。这说明"渠道 × 业务"才是这张架构图真正的中枢。

### 13.6 两处修正（**已确认**）

## 十四、渠道侧对接现状与"人工连接"问题（2026-09-29 补充）

### 14.1 渠道侧已确认合作关系（**CTO 确认**）

| 渠道 | 接了哪块内容 | 接入形态 | 自动化程度 |
|---|---|---|---|
| **携程** | 空手行 | API 对接 | **自动** |
| **东航** | 空手行 | 嵌入 H5 页面（我方页面成交） | **自动** |
| **东航** | 优惠券 | **尚未对接**：优惠券未与东航做 API 对接 | **未接入** |

**差距**：BilionPass 的产品与服务内容有 **9 块**，真正上了渠道的**只有 2 块**（空手行、优惠券）。门票、酒店、租/包车、退税、留学缴费、行程规划、行前购——**渠道侧全部未落地**。

### 14.2 定位再确认：我们是渠道的**服务供给商**

> CTO：*"其实对于渠道来说，我们 bilionpass 只是服务供给商。我们整合了一系列的日本本地服务给到渠道，丰富渠道的能力。"*

- **对渠道**：BilionPass = **服务供给商**（供给侧）
- **对旅客**：BilionPass = 自有平台（bilionpass.com / APP / 小程序）

### 14.3 内容给渠道的三种形态（**CTO 确认**）

`上架销售` ｜ `会员权益` ｜ `积分消耗`（暂不涉及联合营销）

例：酒店给到东航 → 东航可当作**会员权益 / 积分消耗**使用。

**【判断】由此得出一条更准的授权维度**：授权不是"渠道 × 业务"，而是 **渠道 × 内容 × 形态**——同一份内容、不同渠道、不同形态（空手行在携程=上架销售；酒店在东航=权益/积分）。

### 14.4 【判断】贯穿性问题：**平台的关键连接点都在靠人工**

把已确认的事实排在一起：

| 关键连接点 | 现状 | 性质 |
|---|---|---|
| 结算（收款→分账→对账） | **手工对账** | 人工 |
| 渠道对接 | 一条 API、一条 H5、**一条纯人工上传** | 半人工 |
| 履约 | 只有空手行一条打通（佐川 API） | 单点 |
| 风控 | **无** | 缺失 |

**这不是四个独立问题，是同一个问题的四个面**：**平台还没有把"连接"这件事自动化**——而你们的商业模式本质恰恰就是"连接"（把本地供给接到渠道上）。

**推论**：规模化的瓶颈全在人工。每多接一块内容、多接一个渠道（尤其 KOL 可能几十上百个），人工环节就多一份。所以下一阶段该建的，不是更多业务功能，而是**把连接自动化**：内容上架与同步、订单回流、分账与对账、归因。
